แนวคิด ขั้นตอน และวิธีการตรวจสอบข้อมูลซ้ำซ้อนการชำระค่าส่วนกลาง

เอกสารข้อกำหนดเชิงเทคนิคและการออกแบบระบบตรวจสอบก่อนบันทึกข้อมูล (Pre-Validation & Duplicate Prevention Specification)

หน้าจอเป้าหมาย: payment_transfer_smart.php (และ payment_transfer.php)
ประมวลผลหลังบ้าน: model/manage_payment_transfer_smart.php
ตารางฐานข้อมูล: ims_house_payment, ims_house
สถานะเอกสาร: ฉบับสมบูรณ์ (Draft Specification)

1. ปัญหาและช่องโหว่ของการตรวจสอบข้อมูลซ้ำในปัจจุบัน

⚠️ ช่องโหว่ของคำสั่ง SQL เดิมใน manage_payment_transfer_smart.php

เดิมระบบใช้คำสั่ง:

SELECT COUNT(*) FROM ims_house_payment WHERE house_number = :house_number AND period_month_start = :period_month_start AND period_year = :period_year

คำสั่ง SQL ดังกล่าวมีช่องโหว่ร้ายแรง 4 ประการ ที่ทำให้เกิดข้อมูลชำระซ้ำในฐานข้อมูลได้:

1. กรณีชำระหลายเดือน (Partial Overlap) ตรวจไม่พบ

ตัวอย่าง: ลูกบ้านชำระงวดเดือน 1 ถึง 6 ไปแล้ว (Start=1, To=6) ต่อมามีคนมาคีย์ชำระงวดเดือน 3 ถึง 12 (Start=3, To=12)

ระบบเดิมจะเช็คเฉพาะ period_month_start = 3 ซึ่งในระบบเดิมเริ่มที่ 1 จึงไม่พบข้อมูลซ้ำ ทำให้เดือน 3, 4, 5, 6 ถูกบันทึกซ้ำซ้อน!

2. กรณีชำระรายปีแล้วชำระรายเดือนซ้ำ ตรวจไม่พบ

ตัวอย่าง: ลูกบ้านชำระรายปี ม.ค. - ธ.ค. (Start=1, To=12) แล้วต่อมาลูกบ้านลืม เข้ามาจ่ายเดือน ก.พ. (Start=2, To=2)

ระบบเดิมตรวจ period_month_start = 2 ไม่พบ จึงยอมให้บันทึกซ้ำ ทั้งๆ ที่เดือน 2 ถูกจ่ายเหมาทั้งปีไปแล้ว

3. ไม่ตรวจสอบสถานะรายการ (Payment Status) ไม่แยกแยะ

ไม่ได้ตรวจสอบว่ารายการเดิมที่พบเป็น Y (อนุมัติแล้ว) หรือ N (รอตรวจสอบสลิป)

หากมีรายการ N ค้างอยู่ ควรแจ้งเตือนลูกบ้านว่ามีรายการโอนเงินรอบนี้รอการตรวจสอบอยู่ เพื่อป้องกันการโอนซ้ำ

4. การตรวจจับล่าช้า (Post-Upload Check) UX ไม่ดี

ผู้ใช้ต้องกรอกข้อมูลครบ แนบรูปสลิปขนาดใหญ่ (สูงสุด 30MB) และกด Submit ก่อน ระบบถึงจะแจ้งเตือนว่าซ้ำ

ควรมี Real-time Pre-check ทันทีที่เลือกรอบเดือน-ปีบนหน้าจอ

2. รายการสิ่งที่ต้องตรวจสอบทั้งหมด (Checklist 6 มิติ)

ก่อนที่ระบบจะบันทึกข้อมูลการชำระเงินลงในตาราง ims_house_payment จะต้องผ่านการตรวจสอบตาม Checklist ทั้ง 6 มิติต่อไปนี้:

มิติการตรวจสอบ เงื่อนไขและสิ่งที่ต้องเช็ค ผลลัพธ์เมื่อพบปัญหา จุดที่ดำเนินการ
1. ช่วงเดือนทับซ้อน
(Period Month Overlap)		 ตรวจว่าช่วงเดือนที่เลือก [Start_A, To_A] ทับซ้อนกับรายการเดิม [Start_B, To_B] ในปีเดียวกันหรือไม่ ทั้งแบบตรงตัว, ซ้อนบางส่วน, หรือครอบคลุม ปฏิเสธการบันทึก
แสดงเดือนที่ชนกันและเลขที่เอกสารเดิม		 Client (AJAX) + Backend (SQL)
2. ความถูกต้องของบ้านเลขที่และปี - บ้านเลขที่ต้องมีอยู่ในระบบ ims_house
- ปีงวดต้องเป็นตัวเลข 4 หลัก (พ.ศ./ค.ศ. สอดคล้องกัน)
- เดือนเริ่ม (1-12) ต้องไม่เกินเดือนสิ้นสุด		 ปฏิเสธการบันทึก
แจ้งให้เลือกช่วงเดือนให้ถูกต้อง		 Client Form Validate + Backend Sanitization
3. สถานะรายการเดิม (Status) - หากพบรายการทับซ้อนที่มีสถานะ Y (ชำระแล้ว) -> ห้ามบันทึกเด็ดขาด
- หากพบสถานะ N (รอตรวจ) -> แจ้งเตือนว่ามีสลิปรอเจ้าหน้าที่ตรวจสอบอยู่		 บล็อก (ถ้า Y)
เตือนรออนุมัติ (ถ้า N)		 Backend Database Check
4. ป้องกัน Double Submit ป้องกันการกดย้ำปุ่ม "บันทึกข้อมูล" หลายครั้งขณะเน็ตช้า หรือเปิดส่งข้อมูลพร้อมกันหลายแท็บ (Race Condition) Disable ปุ่ม Submit ทันที + เช็ค Duplicate Request Token หรือ Transaction Lock Client JS State + Backend DB Transaction
5. ความซ้ำซ้อนของสลิปโอนเงิน - ตรวจสอบว่าไฟล์สลิปหรือ Hash ของรูปสลิปเคยถูกใช้ในรายการอื่นไปแล้วหรือไม่
- ตรวจสอบ QR Code บนสลิป (ถ้ามี) ว่ายอดเงินและบัญชีตรงกัน		 แจ้งเตือนสลิปซ้ำ Frontend jsQR + Backend File Hash Check
6. ความถูกต้องของยอดเงิน ยอดเงินที่ชำระต้องสัมพันธ์กับ ค่าส่วนกลางรายเดือน x จำนวนเดือน หรือตรงกับยอดโปรโมชั่นรายปีที่กำหนด แจ้งเตือนยอดเงินไม่ตรง Client Calculator + Backend Verification

3. หลักการคำนวณและสูตร SQL สำหรับตรวจจับช่วงเดือนทับซ้อน

การเปรียบเทียบช่วงเวลาสองช่วง $[A_{start}, A_{end}]$ (ช่วงใหม่ที่ต้องการบันทึก) และ $[B_{start}, B_{end}]$ (ช่วงเดิมที่มีในฐานข้อมูล) ในปีเดียวกัน จะเกิดการทับซ้อน (Overlap) ก็ต่อเมื่อ:

📐 สูตรคณิตศาสตร์การตรวจสอบช่วงทับซ้อน (Interval Overlap Formula)

(New_Start ≤ Existing_To) AND (New_End ≥ Existing_Start)

สูตรนี้ครอบคลุมการทับซ้อนทุกรูปแบบ: ซ้ำตรงตัว 100%, ซ้ำช่วงต้น, ซ้ำช่วงท้าย, ซ้ำแบบช่วงใหม่อยู่ข้างใน, และซ้ำแบบช่วงใหม่ครอบช่วงเดิมทั้งหมด

ตารางตัวอย่างกรณีทดสอบการทับซ้อน (Scenario Matrix):

กรณี รายการเดิมในระบบ (B) รายการใหม่ที่กำลังบันทึก (A) การคำนวณตามสูตร ผลลัพธ์
1. ไม่ทับซ้อน (ปกติ) งวด 1 ถึง 3 (ม.ค. - มี.ค.) งวด 4 ถึง 6 (เม.ย. - มิ.ย.) (4 ≤ 3 = เท็จ) AND (6 ≥ 1 = จริง) → เท็จ ผ่าน (บันทึกได้)
2. ซ้ำตรงตัว 100% งวด 1 ถึง 12 (ทั้งปี) งวด 1 ถึง 12 (ทั้งปี) (1 ≤ 12 = จริง) AND (12 ≥ 1 = จริง) → จริง ซ้ำ (ไม่อนุญาต)
3. รายการใหม่อยู่ข้างในรายการเดิม งวด 1 ถึง 6 (ม.ค. - มิ.ย.) งวด 3 ถึง 4 (มี.ค. - เม.ย.) (3 ≤ 6 = จริง) AND (4 ≥ 1 = จริง) → จริง ซ้ำ (ไม่อนุญาต)
4. รายการใหม่ครอบรายการเดิมทั้งหมด งวด 4 ถึง 6 (เม.ย. - มิ.ย.) งวด 1 ถึง 12 (ม.ค. - ธ.ค.) (1 ≤ 6 = จริง) AND (12 ≥ 4 = จริง) → จริง ซ้ำ (ไม่อนุญาต)
5. ทับซ้อนช่วงต้น (Overlap Start) งวด 5 ถึง 10 (พ.ค. - ต.ค.) งวด 1 ถึง 6 (ม.ค. - มิ.ย.) (1 ≤ 10 = จริง) AND (6 ≥ 5 = จริง) → จริง (ชนเดือน 5, 6) ซ้ำ (ไม่อนุญาต)
6. ทับซ้อนช่วงท้าย (Overlap End) งวด 1 ถึง 5 (ม.ค. - พ.ค.) งวด 4 ถึง 9 (เม.ย. - ก.ย.) (4 ≤ 5 = จริง) AND (9 ≥ 1 = จริง) → จริง (ชนเดือน 4, 5) ซ้ำ (ไม่อนุญาต)

คำสั่ง SQL Query ที่ถูกต้องสมบูรณ์สำหรับตรวจสอบในระบบ:

-- ค้นหารายการที่มีการทับซ้อนของงวดเดือนสำหรับบ้านเลขที่และปีที่ระบุ
SELECT 
    id,
    doc_id,
    payment_date,
    period_month_start,
    period_month_to,
    period_year,
    amount,
    payment_status,
    create_by,
    created_at
FROM ims_house_payment
WHERE house_number = :house_number
  AND period_year = :period_year
  AND (:new_month_start <= period_month_to AND :new_month_to >= period_month_start)
ORDER BY period_month_start ASC;

1
ขั้นตอนที่ 1: Real-time Pre-Check บนหน้าจอ (Client-side AJAX)

เมื่อผู้ใช้ทำการเลือก บ้านเลขที่, งวดปี หรือเปลี่ยน เดือนเริ่มต้น / สิ้นสุด:

  • JavaScript ยิง AJAX ไปที่ check_payment_overlap.php หรือ action: CHECK_OVERLAP

  • หน้าจอเรนเดอร์แถบสีสถานะเดือน 1-12 ทันที (สีเขียว = ชำระแล้ว, สีส้ม = รอตรวจ, สีฟ้า = ว่าง)

ขั้นตอนที่ 3: การตรวจสอบความซ้ำซ้อนระดับ Database (Backend Strict Verification)

ที่ฝั่ง Server (model/manage_payment_transfer_smart.php):

  • รันคำสั่ง SQL ตรวจสอบ Overlap Formula (start ≤ period_month_to AND to ≥ period_month_start)

เมื่อผ่านการตรวจสอบทั้งหมด:

  • คำนวณ MD5 / SHA256 Hash ของไฟล์สลิป เพื่อป้องกันการอัปโหลดไฟล์ซ้ำ
  • สร้างเลขที่เอกสาร doc_id ผ่านฟังก์ชัน LAST_DOCUMENT_NUMBER()
  • บันทึกรูปลงเครื่องและส่งขึ้น Google Drive Backup

6.1 ส่วน Backend: ฟังก์ชันตรวจสอบใน model/manage_payment_transfer_smart.php

// --- ตรวจสอบช่วงเดือนทับซ้อนอย่างสมบูรณ์ (Comprehensive Range Overlap Check) ---
$check_sql = "SELECT id, doc_id, period_month_start, period_month_to, period_year, payment_status 
              FROM ims_house_payment 
              WHERE house_number = :house_number 
                AND period_year = :period_year 
                AND (:month_start <= period_month_to AND :month_to >= period_month_start)
              LIMIT 1";

$check_stmt = $conn->prepare($check_sql);
$check_stmt->execute([
    ':house_number' => $house_number,
    ':period_year'  => $period_year,
    ':month_start'  => $period_month_start,
    ':month_to'     => $period_month_to
]);
$existing_payment = $check_stmt->fetch(PDO::FETCH_ASSOC);

if ($existing_payment) {
    $thai_months = ["", "มกราคม", "กุมภาพันธ์", "มีนาคม", "เมษายน", "พฤษภาคม", "มิถุนายน", "กรกฎาคม", "สิงหาคม", "กันยายน", "ตุลาคม", "พฤศจิกายน", "ธันวาคม"];
    $dup_start = $thai_months[$existing_payment['period_month_start']];
    $dup_to    = $thai_months[$existing_payment['period_month_to']];
    $dup_period_desc = ($existing_payment['period_month_start'] == $existing_payment['period_month_to']) ? $dup_start : "{$dup_start} - {$dup_to}";

    if ($existing_payment['payment_status'] === 'Y') {
        echo json_encode([
            'status'  => 'error',
            'code'    => 'DUPLICATE_PAID',
            'message' => "มีรายการชำระค่าส่วนกลางงวด {$dup_period_desc} ปี {$period_year} เรียบร้อยแล้ว (เอกสารเลขที่ {$existing_payment['doc_id']})"
        ], JSON_UNESCAPED_UNICODE);
    } else {
        echo json_encode([
            'status'  => 'error',
            'code'    => 'PENDING_EXISTS',
            'message' => "มีรายการโอนเงินงวด {$dup_period_desc} ปี {$period_year} อยู่ระหว่างรอเจ้าหน้าที่ตรวจสอบ (เอกสารเลขที่ {$existing_payment['doc_id']})"
        ], JSON_UNESCAPED_UNICODE);
    }
    exit;
}

6.2 ส่วน Frontend: Real-time Pre-check ใน payment_transfer_smart.php

// ฟังก์ชันตรวจสอบความซ้ำซ้อนแบบ Real-time เมื่อเลือกงวดเดือน/ปี
function checkPaymentOverlapRealtime() {
    let houseNumber = $('#house_number').val();
    let periodYear = $('#period_year').val();
    let monthStart = $('#period_month_start').val();
    let monthTo = $('#period_month_to').val();

    if (!houseNumber || !periodYear || !monthStart || !monthTo) return;

    $.ajax({
        url: 'model/check_payment_overlap.php',
        type: 'POST',
        data: {
            house_number: houseNumber,
            period_year: periodYear,
            period_month_start: monthStart,
            period_month_to: monthTo
        },
        dataType: 'json',
        success: function(res) {
            if (res.has_overlap) {
                $('#overlap_warning_box').html(
                    `<div class="alert alert-danger"><i class="fa fa-exclamation-triangle"></i> ${res.message}</div>`
                ).show();
                $('#submit_btn').prop('disabled', true);
            } else {
                $('#overlap_warning_box').hide();
                $('#submit_btn').prop('disabled', false);
            }
        }
    });
}

$('#period_month_start, #period_month_to, #period_year').on('change', checkPaymentOverlapRealtime);

7. สรุปประโยชน์ที่จะได้รับหลังปรับปรุง

  • ขจัดปัญหาการบันทึกซ้ำ 100%: รองรับทั้งการชำระรายเดือน, รายหลายเดือน, และรายปี โดยไม่มีช่องโหว่ของการซ้อนทับ
  • ประสบการณ์ผู้ใช้งานที่ดีขึ้น (Better UX): ทราบสถานะเดือนที่ว่างทันทีก่อนอัปโหลดสลิป ไม่ต้องรอลุ้นตอนกดส่ง
  • ลดภาระงานของเจ้าหน้าที่นิติบุคคล: ลดปัญหาสลิปซ้ำ ยอดเงินไม่ตรง และไม่ต้องเสียเวลาลบข้อมูลซ้ำในหน้า show_duplicate_payments.php
  • ความถูกต้องของรายงานบัญชีและ GL: ป้องกันการลงบัญชีรายได้และภาษีซ้ำซ้อนในระบบบัญชีหมู่บ้าน

เอกสารประกอบการพัฒนาระบบชำระค่าส่วนกลางอัจฉริยะ โครงการ พีเอสโฮม 33
