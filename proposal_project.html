Technical Proposal

การยกระดับสถาปัตยกรรมโครงการสู่มาตรฐานเดียวกัน (Framework Unification)

แนวทางการปรับปรุงระบบงาน, การประมวลผลข้อมูล, การแสดงหน้าจอ และการออกรายงาน ให้อยู่ในทิศทางเดียวกัน

แนวคิดหลักในการปรับปรุงระบบ (Core Philosophy)

ปัจจุบัน ระบบงานของโครงการมีความหลากหลายทางด้านการออกแบบเนื่องจากการพัฒนาแบบต่อยอด (เช่น หน้าแบบดั้งเดิมใช้การเขียนผสม PHP/HTML, หน้าใหม่รองรับ LINE LIFF ใช้ AJAX สื่อสารหลังบ้านแบบ JSON API, ส่วนการออกรายงานบางส่วนใช้ mPDF ผสมกับคำสั่ง SQL ที่เขียนแบบแยกอิสระ) แนวทางในการปรับปรุงโครงการนี้ให้เข้าสู่มาตรฐานเดียวกัน มีทางเลือกในการจัดการดังต่อไปนี้:

แนวทางที่ 1: การเปลี่ยนผ่านทีละส่วน (Progressive MVC)

แนวคิด: ค่อยๆ ปรับปรุงโดยไม่ต้องล้างเขียนใหม่ทั้งหมด แต่แยกโค้ดออกเป็นสัดส่วนตามแนวคิด Model-View-Controller (MVC) โดยประยุกต์ใช้โครงสร้างที่มีอยู่

  • Model: ย้าย SQL Query จากหน้าจอไปไว้ในโฟลเดอร์ classes/ หรือ models/
  • View: แยกไฟล์ HTML/JS ออกจาก Logic การดึงข้อมูล
  • Controller: ใช้ API Endpoint ร่วมกันเป็นจุดประมวลผลหลัก
แนวทางที่ 2: การพัฒนาใหม่ทั้งหมดด้วย Laravel Framework

แนวคิด: การย้ายโครงการทั้งหมดขึ้นสู่ระบบ Laravel Framework ซึ่งเป็นเฟรมเวิร์ก PHP ยอดนิยมระดับสากล เพื่อสถาปัตยกรรมระดับอุตสาหกรรมในระยะยาว

  • Eloquent ORM: จัดการฐานข้อมูลและ Relation ได้เสถียร
  • Blade Engine: การนำเอา UI หน้าจอ/เลย์เอาต์กลับมาใช้ซ้ำแบบสม่ำเสมอ
  • API Routing: มีระบบความปลอดภัยและระบบตรวจสอบสิทธิ์ที่รัดกุม
ข้อเสนอแนะเชิงกลยุทธ์: แนะนำให้ใช้ แนวทางที่ 1 (Progressive MVC) ในเบื้องต้น เนื่องจากโครงการเป็นระบบที่รันบนระบบจริง (Production) การจัดเรียงโฟลเดอร์และแยก Logic จากการสืบค้นเดิม จะมีความเสี่ยงต่ำและค่าใช้จ่ายในการพัฒนาน้อยกว่ามาก ก่อนพิจารณาย้ายไปสู่เฟรมเวิร์กเต็มรูปแบบในเวอร์ชันถัดไป

สถาปัตยกรรมการประมวลผล บันทึกข้อมูล และการคำนวณ

เพื่อยกระดับทิศทางเดียวกันในแง่ของ Logic การบันทึกและการคำนวณ ระบบควรนำเอา **Service Layer** และ **Data Access Object (DAO)** เข้ามาประยุกต์ใช้เพื่อแก้ปัญหาโค้ดสปาเก็ตตี้

1. Request Layer (Client)
ส่งข้อมูลผ่าน AJAX JSON จากเบราว์เซอร์ไปที่ Single API Endpoint ปลายทาง
2. Validation & Security Service
ตรวจสอบสิทธิ์การใช้งาน (Session / Token API) และความถูกต้องของข้อมูลนำเข้า (Data Type, XSS Prevention)
3. Business Service Layer (การประมวลผลและการคำนวณ)
ประมวลผลความต้องการทางธุรกิจ เช่น การคำนวณส่วนลดตามช่วงโปรโมชั่น, คำนวณเบี้ยปรับชำระล่าช้า, หรือการสแกนสลิปผ่าน API
4. Repository/DAO Layer (การเข้าถึงข้อมูล)
ทำหน้าที่รัน SQL Statement เพื่อเขียน/อ่านข้อมูลกลับสู่ฐานข้อมูลผ่าน PDO (PDO Prepared Statements 100%)

การปรับปรุงทิศทางการเขียนโปรแกรม (Programming Paradigm Shift)

  • การคำนวณทางคณิตศาสตร์ที่เป็นระบบเดี่ยว (Centralized Calculation):

    แยกฟังก์ชันคำนวณค่าส่วนกลาง, คำนวณภาษีหัก ณ ที่จ่าย หรือยอดเงินเดือน ออกจากไฟล์หน้าจอ โดยจัดทำเป็นคลาสบริการ (เช่น CommonFeeService.php) เพื่อไม่ให้เกิดปัญหาสูตรคำนวณไม่ตรงกันในแต่ละหน้าจอ

  • สถาปัตยกรรมความถูกต้องในการบันทึกข้อมูล (Database Transactions):

    การบันทึกรายการที่ผูกมัดหลายตารางพร้อมกัน (เช่น การจ่ายเงินของสมาชิก จะต้องบันทึกใบเสร็จ ims_house_payment และบันทึกสมุดบัญชีแยกประเภททั่วไป ims_gl พร้อมกัน) ต้องทำงานภายใต้ Transaction ($conn->beginTransaction()) เสมอ เพื่อลดปัญหาข้อมูลไม่สอดคล้องหากมีคำสั่งใดคำสั่งหนึ่งล้มเหลว

  • การกรองข้อมูลความปลอดภัย (Input Sanitization):

    สร้างคลาสช่วยกรองข้อมูล (Helper class) เช่น `Security::sanitize()` เพื่อล้างข้อมูลภัยคุกคาม XSS และ SQL Injection แทนการใช้ฟังก์ชันดิบของ PHP สะเปะสะปะ

มาตรฐานการแสดงและพิมพ์รายงาน (Reporting & Document Printing Standards)

ระบบออกรายงานควรปรับเปลี่ยนให้อยู่ในมาตรฐานเดียวกัน เพื่อลดปัญหาเรื่อง Layout เสีย, ภาษาไทยไม่แสดงผล หรือความช้าในการเรนเดอร์ข้อมูล

การแสดงรายงานบนหน้าจอ (Web Reports)

  • ใช้ DataTables Engine เป็นมาตรฐานเดียว: ทุกหน้าจอแสดงผลข้อมูลและตาราง ควรรองรับการค้นหา การเรียงลำดับ และการแบ่งหน้าจอ โดยใช้โครงสร้าง DataTables Server-Side Processing เพื่อไม่ให้เบราว์เซอร์ค้างเมื่อข้อมูลมีจำนวนมาก
  • การแสดงแผนภูมิเชิงสถิติ: พัฒนามาตรฐานการแสดงผลแผนภูมิด้วย Chart.js เชื่อมโยงผ่าน API เพื่อความเป็นสม่ำเสมอของดีไซน์
  • การส่งออกข้อมูลดิบ (Data Export): ทำปุ่มดึงออกเป็น Excel (.xlsx) และ CSV โดยดึงจากข้อมูลชุดเดียวกันกับที่แสดงผลในตารางรายงานบนหน้าเว็บ

การพิมพ์เอกสารและ PDF (Document Printing)

  • รวมศูนย์ Library mPDF: กำหนดให้ PDF ทุกใบ (สลิปเงินเดือน, บิลค่าส่วนกลาง, ใบเสร็จรับเงิน) สร้างผ่าน Library mPDF ที่ติดตั้งผ่าน Composer ในที่เดียว
  • Template-Driven PDF: สร้างไฟล์เทมเพลต HTML/CSS แยกไว้ต่างหาก แล้วใช้คำสั่ง `render()` นำตัวแปรไปแทนที่ข้อมูล เพื่อไม่ให้เกิดการเขียนสคริปต์ mPDF แทรกปนเปไปกับโค้ด SQL
  • ฟอนต์มาตรฐาน (Sarabun): กำหนดค่า mPDF ให้ใช้ฟอนต์ TH Sarabun PSK / Sarabun เป็นดีฟอลต์สำหรับทุกภาษาไทยเพื่อความเป็นระเบียบและประหยัดพื้นที่
โครงสร้างคลาสสากลสำหรับออกรายงาน PDF (Helper Class Concept) php 
<?php
namespace App\Helpers;

use Mpdf\Mpdf;

class ReportRenderer {
    protected $mpdf;

    public function __construct() {
        // ตั้งค่าฟอนต์และคุณสมบัติมาตรฐานที่เดียว
        $this->mpdf = new Mpdf([
            'fontDir' => array_merge((new \Mpdf\Config\ConfigVariables())->getDefaults()['fontDir'], [
                __DIR__ . '/../../fonts',
            ]),
            'fontdata' => (new \Mpdf\Config\FontVariables())->getDefaults()['fontdata'] + [
                'sarabun' => [
                    'R' => 'Sarabun-Regular.ttf',
                    'B' => 'Sarabun-Bold.ttf',
                ]
            ],
            'default_font' => 'sarabun',
            'format' => 'A4',
            'margin_left' => 15,
            'margin_right' => 15,
            'margin_top' => 15,
            'margin_bottom' => 15
        ]);
    }

    public function renderPdf($templatePath, $data, $outputName = 'document.pdf') {
        // อ่าน HTML จาก Template แยกส่วน
        ob_start();
        include($templatePath);
        $html = ob_get_clean();

        $this->mpdf->WriteHTML($html);
        $this->mpdf->Output($outputName, \Mpdf\Output\Destination::INLINE);
    }
}
?>

ข้อกำหนดรูปแบบหน้าจอและดีไซน์ UI (Unified Design System)

เพื่อหลีกเลี่ยงความสับสนและไม่เป็นทิศทางเดียวกันในเรื่องการออกแบบโทนสี ฟังก์ชัน และการตอบสนอง ระบบควรมีแนวทางการตั้งค่าสไตล์กลางดังนี้:

1. ระบบสีหลักและโทนของระบบ (System Color Palette)

กำหนดให้เปลี่ยน CSS ของระบบทุกตัวให้ใช้ระบบตัวแปร CSS (CSS Variables) เพื่อให้สามารถปรับธีมหรือสีได้จากที่เดียว แทนการกำหนดค่าสีแบบ Hard-code ในแต่ละไฟล์:

ตัวแปรสไตล์ รหัสสีหลัก จุดประสงค์การใช้
Primary Slate #0f172a เมนูด้านข้าง (Sidebar), สีหัวตารางหลัก, หัวข้อสำคัญ
Accent Blue #2563eb ปุ่มกดหลัก (Primary Buttons), ลิงก์เชื่อมโยง, ข้อมูลสถานะ Active
Soft Success Green #10b981 ปุ่มบันทึกข้อมูล, ป้ายสถานะยืนยันยอดเงินสำเร็จ (Approved/Verified)
Clean Light Gray #f8fafc สีพื้นหลังหลักของหน้าเว็บ (Background)

2. การสร้างคอมโพเนนต์ส่วนกลาง (Reusable UI Components)

  • ระบบโครงสร้างฟอร์ม (Form Patterns): ทุกแบบฟอร์ม (เช่น บันทึกชำระเงิน, บันทึกประวัติเครื่องมือ) ต้องจัดระเบียบการกรอกข้อมูล 2 คอลัมน์สำหรับเดสก์ท็อป และ 1 คอลัมน์สำหรับโทรศัพท์ (Responsive layout)
  • กล่องตอบโต้และป๊อปอัปแจ้งเตือน (Modals & Alerts): ยื่นยันผลการประมวลผลด้วย AlertifyJS หรือ SweetAlert2 เป็นค่าหลักสำหรับทุกหน้า ไม่ควรใช้คำสั่ง `alert()` หรือ `confirm()` พื้นฐานของเบราว์เซอร์ เพื่อให้ความรู้สึกแบบ Modern Premium
  • เลย์เอาต์ระบบ (Main Wrapper Layout): กำหนดโครงสร้าง `sidebar` และ `header` ให้เป็นหนึ่งไฟล์ถาวร (เช่น `layouts/app.php`) แล้วใช้ระบบ `Content Section` เข้าไปครอบแทนการรันคำสั่ง `include` ซ้ำๆ ทุกหัวกระดาษของทุกไฟล์

แผนและขั้นตอนการดำเนินการย้ายระบบ (Migration Roadmap)

เพื่อให้การปรับปรุงโครงสร้างโครงการเป็นไปได้อย่างปลอดภัย ข้อมูลไม่เสียหาย และระบบยังคงเปิดให้บริการได้ตามปกติในระหว่างการปรับปรุง แนะนำให้แบ่งการดำเนินงานเป็น 5 ระยะดังนี้:

ระยะที่ 1: การจัดเก็บสถาปัตยกรรมส่วนควบคุมกลาง (สัปดาห์ที่ 1 - 2)

- ตั้งค่าไฟล์ autoloading (เช่น Composer PSR-4) เพื่อดึงคลาสต่างๆ เข้ามาใช้งานอัติโนมัติ
- ทำการปรับปรุงโค้ดเชื่อมต่อฐานข้อมูลใน `config/connect_db.php` ให้รองรับ PDO รูปแบบ Singleton เพื่อจำกัดสิทธิ์ทรัพยากร
- ปรับปรุงสคริปต์ Sidebar / Header ใน `includes/` ให้เป็นระเบียบและใช้ CSS ตัวแปรร่วมกัน

ระยะที่ 2: ดึง SQL และ Logic ออกจากหน้าแสดงผล (สัปดาห์ที่ 3 - 4)

- ย้ายโค้ด SQL จากส่วนจัดการข้อมูลหลัก (เช่น `manage_expenses.php`, `manage_payroll_data.php`) เข้ามาทำงานใน Class Services - เขียน Unit Test เล็กๆ สำหรับฟังก์ชันที่มีการคำนวณเงินหรือภาษี เพื่อทดสอบว่าให้ค่าผลลัพธ์การคำนวณที่ถูกต้องสม่ำเสมอ

ระยะที่ 3: ปรับปรุงการเชื่อมโยงระบบด้วย API (สัปดาห์ที่ 5 - 6)

- ทำความสะอาดฟอร์มการส่งค่า โดยปรับให้ส่งข้อมูลผ่านรูปแบบ JSON AJAX ไปประมวลผลที่หลังบ้าน (เช่น ย้ายโค้ดรับเซฟใน `model/` ไปเป็น API Controllers) - จัดทำระบบส่งรหัส Error และ Success รูปแบบ JSON ที่มีสัญลักษณ์โครงสร้างมาตรฐานเดียวกันทั้งโครงการ

ระยะที่ 4: รวมมาตรฐานการออกรายงานและหน้าตา (สัปดาห์ที่ 7 - 8)

- ย้ายการสร้างเทมเพลตรายงานการเงินและรายงานค่าส่วนกลางเข้าสู่ระบบ Template-Driven PDF - ปรับเปลี่ยนตารางหน้าจอแสดงผลรายงานต่างๆ ในระบบหลังบ้านให้ทำงานผ่าน DataTables Server-Side Processing

ระยะที่ 5: การทดสอบขีดความสามารถและความปลอดภัยปลายน้ำ (สัปดาห์ที่ 9)

- ทดสอบความมั่นคงปลอดภัย (Security Testing / SQL injection vulnerability scanning) - นำโค้ดระบบใหม่ไปติดตั้งทดแทนตัวเดิมทีละโมดูลแบบเกลี่ยยอดงาน (Rolling deployment)

ข้อควรระวัง: ห้ามทำการปรับโครงสร้างใหญ่ของโค้ดในระบบจริงโดยไม่มีระบบสำรอง (Sandbox หรือ Version Control Branching) ควรสร้าง git branch ใหม่แยกต่างหากเพื่อทำการทดลองระบบ และจัดเตรียมแผนการถอยกลับระบบหากมีปัญหา (Rollback Plan) ในทุกๆ ขั้นตอน
